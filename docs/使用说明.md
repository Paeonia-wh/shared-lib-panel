# 使用说明（写给 AI 会话看的）

> **读者：被用户叫来"用这个项目库干活"的 AI 会话。**
> 部署那一步在 [`部署.md`](部署.md)；这份讲**装完之后怎么干活**。
> 核心只有一句：**你的活记进库，下一个人（或下一个 AI）才能接着干。**

---

## 0. 这个库是怎么运转的（先看懂这个，后面全通）

```
用户 → AI 会话（你）→ 你干活 → 把结果写进库 → 面板显示进度
                                    ↓
                      用户换会话时，把「复制块」粘给下一个 AI
                                    ↓
                      下一个 AI 读库 → 知道做到哪、坑在哪、下一步干什么
```

**所以你在库里的每一个动作，都是在给"下一个接手的人"留信息。**
写不清楚 = 那个人（可能是换了 AI 的你）要从头再摸一遍。

---

## 1. 你最常做的三件事

| 用户说 | 你要做的 | 用哪个工具 |
|---|---|---|
| "接着做 XX" | 读上下文 → 干活 → 写检查点 → 收尾 | `project_context_pack` / `project_checkpoint` / `project_task_update` |
| "把这活拆成任务" | **先问清要求** → 建卡 → 卡片自带验收判据 | `project_task_create` / `project_task_contract` |
| "这个地方也要做" | 先判断**该不该建新卡**，再决定建卡还是往老卡补 | 同上 |

⚠️ **三件事都有"先问用户"的门** —— 见第 3 节，**别跳过**。

## 2. ★ 怎么建卡（建卡是"把要求定下来"，不是"起个名字"）

### 建卡时必须想清楚的四个字段

```
task_key     英文短横线小写（order-cart），全项目唯一。**只用来指代，不给人看**
title        给用户看的名字（购物车与结算流程）—— 用户能从面板上认出来
contract     合同：目标 + 验收标准 + 约束 ←★ 最重要的一个
description  库里的原始说明（**建完就改不了了**，一次写对）
```

### ★ contract 怎么写（这是建卡的灵魂）

```json
{
  "objective": "购物车与结算全流程可用，含优惠券叠加",
  "acceptance": [
    "file_exists:src/cart.ts",
    "tests_pass:npm test -- cart"
  ],
  "constraints": ["不动会员模块"]
}
```

**`acceptance` 里优先写「机器能查的判据」** —— 平台支持这些前缀：

| 判据 | 含义 | 例 |
|---|---|---|
| `file_exists:<路径>` | 文件在不在 | `file_exists:src/cart.ts` |
| `tests_pass:<命令>` | 命令跑得过不过 | `tests_pass:npm test` |
| `grep_present:<文件>:<关键字>` | 文件里有没有这个关键字 | `grep_present:src/cart.ts:applyCoupon` |
| `grep_absent:<文件>:<关键字>` | 文件里**不该**有 | `grep_absent:src/cart.ts:TODO` |

**为什么值得花时间写判据**（不是形式主义）：
```
① 你自己知道"做到什么算完" —— 否则你会自己编一个标准
② 对账时平台能**自动跑**判据当证据；没有判据就只能"读一遍说通过"
③ 实测现实：库里 51 个有合同的任务里，含可判定判据的 = 0 个
   —— 这是本项目当前最大的质量问题
```

**确实只能人看的活**（设计稿、文案）→ 就写人话（`"配色符合设计稿"`），
但收尾时把"人该看什么"写进检查点。

### 建卡前的三个判断（**顺序别反**）

```
① 这块活该不该建新卡？
   还在某个已有任务的合同范围内 → **别建新卡**，那是往老卡里补活
② 计划锁没锁？
   没锁 → project_task_create 直接建
   锁着 → 只能 project_plan_propose 提案，**且要另一个会话来批**（不能自批）
③ 依赖写了吗？
   depends_on 写真的会卡住这条的任务 key。**别写一句人话**（"等公司主体办证"）
   —— 那样的依赖在库里查不到，接手的人会一直找
```

## 3. ★★ 动手前的门：**先问用户，别直接开工**

**这是硬规矩，不是建议。** 三种情况：

### 情况 A · 任务的要求还没定清楚

```
判据：合同里既没有 objective，也没有一条可判定的 acceptance
→ 你要做的第一件事是问用户：
   「这件事做成什么样算完？拿什么证明它完了？」
→ 问清后用 project_task_contract 补上合同，再开工
```

### 情况 B · 有目标，但没有机器能查的判据

```
→ 问用户能不能加一条（file_exists: / tests_pass: 这种）
→ 如果确实只能人看 → 继续做，但收尾时写清"人该看什么"
```

### 情况 C · 要建新卡之前，先核对那些"已完成"是不是真的

```
⚠ 这是个真问题：库里标 done 是**上一个会话说的**，不是平台验的。
  换会话时很容易"为了收口就标了 done、其实还差一点"。
  你拿这个假的完成当既成事实往上垒，**后面全歪**。

→ 问用户（面板那块会给你现成话术）：
   「这几张标着"已完成"的卡，您认为真的做完了吗？还是当时为了收口先标上的？」
→ 用户说"没做完" → project_task_reopen 退回队列
→ 用户说"都做完了" → **把他这句话记进检查点**（这是"经过人确认"的证据）
```

## 4. 干活期间：检查点怎么写（**只有五项，一个都别省**）

```json
{
  "completed":   ["做完了什么 —— 具体到文件/命令，别写'完成了开发'"],
  "not_done":    ["发现了但没做的 —— ★ 这是传给下一个会话的唯一通道"],
  "pitfalls":    ["踩过的坑 —— ★ 最值钱的一项，别省"],
  "blockers":    ["卡住你的外部依赖"],
  "next_action": "下一步该干什么（一句话，能直接照着做）"
}
```

**几个反例（都是实测见过的）**：

| 别这样写 | 为什么 |
|---|---|
| `completed: ["完成了开发"]` | 下一个会话学不到任何东西 |
| `pitfalls: []`（明明踩了） | **坑是最值钱的** —— 你踩过、别人不用再踩 |
| `not_done: []`（明明有没做的） | 那个活就**消失了**，没人知道它还在 |
| `next_action: "继续推进"` | 等于没说。要能直接照着做 |

**写检查点的时机**：
```
· 完成一个任务 → 记
· 一个会话做了多个任务 → **每个任务都记**（不能只记最后一轮）
· 要中断/换会话之前 → **必须记**（这是"冻现场"，不记就等于全丢）
```

## 5. 收尾顺序（**顺序反了会把自己锁死**）

```
1. 写检查点（五项）
2. 发产出      project_artifact_publish —— path 必须指向**真实存在的文件**
3. 跑 preflight 验判据
4. 标 done
```

**两条铁律**：

```
· ★ **没做完的绝对不要标 done**
  标了 done，面板说这件事完了、下个会话以为不用管、对账时拿不到东西。
  而且平台**禁止 done 直接改回 running**，要退只能走：
      project_task_reopen(task_id=<id>, session_id=<你>, reason="<为什么>")

· ★ **产出必须是真的文件**
  只报路径不落地 → 对账会判 rejected。
  平台每 60 秒核对一次：文件还在不在、内容有没有被改过。
```

## 6. 面板上那些「复制块」是什么、你该怎么用

面板上有几段**中文指令**，用户会复制出来粘给会话。**你要认识它们**：

| 块 | 用户什么时候用 | 你该怎么做 |
|---|---|---|
| **【项目现状 · 项目名】** | 想知道"这个项目现在什么情况" | **先汇报局面，再问用户要推哪一件** —— 别自己挑一个开工 |
| **【继续做 · 项目/任务】** | 要接着干某个任务 | 按 `project_task_dispatch` 领活的流程做（块里写了） |
| **【待验收 · 项目/任务】** | 任务做完了等对账 | **别重做**。找**另一个会话**来对账（对账人不能是任务所有者） |
| **【已完成 · 项目/任务】** | 想看这个任务做过什么 | 只看；真要接着做 → 先 `project_task_reopen` |
| **【给 XX 加任务】** | 要把新活拆成卡 | **先核对"已完成"是不是真的**，再建卡 |
| **【记录进共享库】** | 干完活要收尾 | 按五项检查点 + 收尾顺序做 |
| **【开始一个新东西】** | 从零开始一个项目 | **先问用户要干什么**，别自己挑一个就开始做 |

**这些块里如果提到某个 `docs\xx.md` 路径**：
```
那只是"想更细再看" —— **路径打不开就忽略**，块里该说的都说全了。
别为了读一个不存在的文件停下来。
```

## 7. 对账（review）怎么做

```
谁来做：**另一个会话**（对账人不能是任务所有者 —— 自己做会报
        "The task owner cannot verify its own task"）
怎么做：project_reconcile(project=…, task_id=…, status="verified"/"rejected",
                          reviewer_session_id=<另一个会话 id>, summary="结论")
```

```
· 平台会**自动跑合同里的可判定判据**，结果作为证据留档
  → 所以判据写得好不好，直接决定对账是"读一遍说通过"还是"真有证据"
· 发现没做完 → status="rejected"，**必须写清 location / defect / fix**
  （只写 rejected 不写细节，下一个会话除了"没过"什么都得不到）
```

## 8. 几条边界（**做之前先想一下**）

```
· 别改已 done 的任务 —— 走 reopen
· 别把 done 当"重做一遍"的许可 —— done 是"看交接"
· 别自己编验收标准 —— 那是把"做完了"的定义交给你自己
· 别为了看起来有进展就建一堆空卡 —— 卡是要有人做的
· 别信检查点里"当时的变通办法" —— 那反映的是**当时的库**，
  工具和行为后来变过；照抄前先核对，或者直接问用户
· 用户没答"先问清楚"那些问题之前，**不要建卡、不要改状态、不要开工**
```

## 9. 一句话总结这份文档

> **你写的每一条记录，都是给"下一个接手的人"看的。**
> 他只是换了个会话（甚至换了个 AI），他不认识你、看不到你的聊天记录 ——
> **你写进库的东西，就是他全部的信息来源。**
